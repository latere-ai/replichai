# 041f — OpenAI Responses runs a session

**Status:** designed, not built. Implement only after 041a–041e are built and reviewed against the then-current OpenAI API; hosted shell/container features are evolving.

**Scope:** add `openai-responses`, a direct OpenAI managed-session runtime over background Responses and hosted-shell containers. Implement durable restart, normalised events/artifacts/usage, cancellation/release, and a portable rubric/revision loop. Register it explicitly in the runtime catalog. Do not weaken unsupported sandbox semantics.

**Depends on:** [041e](041e-anthropic-conforms-to-the-session-contract.md). Current API basis: OpenAI's [Responses reference](https://developers.openai.com/api/reference/cli/resources/beta/subresources/responses), [response creation contract](https://developers.openai.com/api/reference/cli/resources/responses/methods/create), and [Containers reference](https://developers.openai.com/api/reference/cli/resources/containers).

## Why this is not an Anthropic-shaped adapter

OpenAI has no need for replichai to create a persistent environment and agent revision. The public primitives that match this product are a stored background Response, a hosted-shell container reference, response retrieval/cancellation, and container file list/content/delete. The response state includes queued/in-progress/completed/failed/cancelled/incomplete, while the container holds working files.

One replichai session may require several Responses: deterministic bootstrap, worker execution, rubric evaluation, and a revision when evaluation fails. The stable `SessionRef.ID` is therefore generated by the adapter; the locator journals the one container and the ordered response stages. Treating the first response id as the whole session would lose later usage, cancellation target, transcript, and restart state.

## Capability gate

The adapter is enabled only with explicit `OPENAI_API_KEY`, configured tier-to-model mappings, rate coverage, and an API feature version known to support the required hosted-shell/container behaviour. It does not guess a “first” model or assume every Responses model supports hosted shell. Operator configuration declares models; startup validates syntax and rate coverage, while the first real request still handles account/model availability as a typed policy error.

Capabilities advertise only what the current API can enforce:

- background stored Responses with retrieve and cancel;
- hosted-shell containers, uploaded/container files, and file-content retrieval;
- network `none` and explicit domain `allowlist`, including domain-bound secrets;
- supported memory sizes and expiry window;
- `pip` packages/bootstrap through a verified bootstrap response;
- attachments and read-write Git repositories through container materialisation;
- portable evaluation/revision.

An unrestricted `NetworkOpen` request is **unsupported** when the container API offers only disabled/allowlist policy. It is rejected before container creation; the adapter never turns “open” into a guessed allowlist. This means an existing open-network audit is eligible for OpenAI only after its route supplies an explicit sufficient domain policy. Experiments/cohorts with disabled or known-domain access can route immediately. The Latere/Cella path in 041g is the alternative for policies Cella can enforce differently.

Zero-data-retention or account policy that prevents stored/background retrieval is also unsupported for detached/resumable sessions. The adapter reports this during a capability probe where the API exposes it, or as a typed start policy error; it does not claim restart durability in a mode that cannot retrieve the Response.

## Start and locator journal

`Start` validates everything, generates a stable session id and deterministic idempotency namespace, then:

1. uploads/materialises input files required to create the container;
2. creates one container with expiry, memory, and exact network/domain-secret policy;
3. creates a background bootstrap Response against that container when packages, repository, or bootstrap argv are present;
4. otherwise creates the background worker Response directly;
5. returns revision 1 with container id, current response id, stage, owned file ids, response ids, and idempotency namespace.

Instructions are sent as the developer/system instruction and the task as user input. When a later Response uses prior state, instructions are sent again because Responses does not carry earlier instructions merely from `previous_response_id`. Provider/model/requested service tier are stored in adapter metadata; the actually returned service tier becomes `ModelRef.BillingVariant`, because OpenAI documents that it may differ from the requested tier.

Every stage-creating POST uses an idempotency key derived from `(session id, stage kind, revision number)`. `Poll` may advance the orchestration only after observing the current response terminal. It creates at most one next stage, returns a higher-revision locator, and waits for the controller's CAS checkpoint before another call. A crash/retry at the POST boundary resolves the same response through the same idempotency key.

The locator contains ids and enum state only: no instructions, task, rubric, domain-secret value, attachment bytes, transcript, API key, or repository credential.

## Verified bootstrap and repository

OpenAI exposes shell through the model, not as an ordinary client exec endpoint. Bootstrap is therefore a dedicated constrained Response, not prose prefixed to the research task:

- the adapter writes a manifest containing exact package/bootstrap argv and expected repository destination;
- the bootstrap response is instructed to execute only that manifest with hosted shell and return a strict result schema;
- tool outputs must show every argv entry, exit code zero, and the expected files/digests before the worker stage can start;
- deviation, missing tool evidence, timeout, or nonzero exit makes the session failed and prevents the worker task.

Repository materialisation clones/checks out the declared revision into the declared destination. Read-write mode configures push authority using a host-bound secret supported by container network policy; the secret value is resolved by the adapter at request time and never appears in prompts, argv, locators, or events. Publication still verifies the remote committed tree, so a claimed push without the expected GitHub state fails evidence retention.

If the API cannot deliver a repository credential without exposing it to the model/container beyond the requested secret contract, read-write repository capability is disabled and audit requests fail preflight. No URL-with-token fallback exists.

## Portable evaluation and revisions

OpenAI Responses has no direct equivalent of Anthropic Managed Agents' `user.define_outcome`. A non-nil `EvaluationSpec` is implemented as an adapter-owned loop:

1. after a worker Response completes, create a fresh evaluator Response with the rubric, normalised worker transcript, and bounded artifact manifest/read access;
2. require a strict structured result: decided pass/fail plus reasons and revision feedback;
3. on pass, produce terminal `done` with verdict;
4. on fail with remaining budget, create a revision Response in the same container with the evaluator feedback and original instructions/task, then evaluate again;
5. on exhausted budget, produce terminal `done` with a decided failing verdict, matching Anthropic product semantics rather than runtime failure.

The evaluator is a separate Response without the worker's assistant role or self-authored verdict in its context. It may use the same resolved model in v1; a separately priced evaluator model is a future route-policy extension. Malformed/undecided evaluation is a runtime failure, never an inferred pass/fail.

`Evaluation == nil` creates no evaluator Response and returns `Verdict == nil`. All response ids and stage usage are journaled and cumulative. Cancellation targets only the current in-progress Response and prevents creation of another stage.

## Events, artifacts, status, and release

`Poll` retrieves the current Response and maps queued/in-progress to neutral pending/running; completed advances or terminates; failed/cancelled/incomplete map to failed with distinct terminal reason. A completed worker is not terminal while evaluation/revision remains.

`Events` folds output items and tool-call records from every journaled Response into stable `(stage, response id, item id)` event ids and chronological order. It exposes normalised per-event usage where OpenAI reports it and retains raw items as evidence. Status usage sums all bootstrap, worker, evaluator, and revision Responses, subtracting cached input from total input exactly once and recording the actual service tier.

`ListArtifacts` lists container files with pagination, excluding declared input files and adapter-internal manifests. Paths are normalised and contained. `FetchArtifact` uses container file-content retrieval and enforces configured total/file limits. The Git repository remains the publication source of truth; container files are supplementary evidence.

`Cancel` calls response cancellation only for an active cancellable Response and is idempotent around terminal/not-found outcomes. `Release`, after retention, deletes owned stored Responses/files where supported and then deletes the owned container. It records partial cleanup for retry. Expiry is a safety net, not the normal cleanup mechanism.

## Acceptance criteria

1. `openai-responses` passes the complete managed runtime conformance suite for advertised capabilities and exceeds 90% statement coverage.
2. Mock-server tests assert exact container/network/file and background Response payloads, instruction/task role separation, `store`/restart behavior, idempotency keys, redaction, and actual service-tier capture.
3. A table-driven restart test crashes after each remote stage creation but before/after locator checkpoint; resume never duplicates a Response, loses the active id, or double-counts usage.
4. Bootstrap tests require exact argv/tool evidence and exit zero before worker start; deviation fails. Open network, unsupported package managers, and unsafe repository credentials fail before the first HTTP mutation.
5. Graded tests cover immediate pass, fail-then-revise-pass, exhausted failing verdict, malformed evaluator, and cancellation during each stage. Ungraded creates no evaluator.
6. Transcript tests merge all stage events with stable ids; cached input, output/reasoning detail, response-stage totals, and actual billing variant reconcile exactly once.
7. Artifact tests cover pagination, input/internal exclusion, traversal rejection, byte limits, fetch before release, and unavailability after release.
8. Partial failures at file/container/bootstrap/worker/evaluator/revision creation roll back or retain a resumable checkpoint according to 041b; no container or response is orphaned in mock inventory.
9. A provider-table end-to-end test drives the same normalized ungraded session through mocked Anthropic and OpenAI boundaries and compares terminal state, transcript roles, artifact bytes, and usage semantics.
10. An opt-in live smoke (key/account/model gated, never required for unit CI) runs one tiny disabled-network session, retrieves an artifact, cancels a second session, releases both, and records no secret.

## Out of scope

- Claiming unrestricted internet when only allowlists are enforceable.
- OpenAI Workspace Agents: the direct runtime uses public Responses/container lifecycle because replichai requires programmatic retrieval, cancellation, artifacts, and durable references.
- OpenAI's beta multi-agent feature. Replichai needs one reproducible worker/evaluator loop first.
- Using Lux's OpenAI compatibility surface for this adapter. Lux's documented compatibility Responses subset is stateless, while this runtime requires stored background retrieval; 041g uses Lux natively through Topos instead.
- Selecting a direct OpenAI runtime per researcher. Routing remains operator policy.
